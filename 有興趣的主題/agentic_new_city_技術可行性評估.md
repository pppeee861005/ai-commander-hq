## MVP 版本的降級方案

### 降級路徑（如果遇到技術困難）

| 計劃 | 降級方案 | 影響 |
|------|--------|------|
| **政府建照 API 自動同步** | 人工每週填表一次 | 失去實時性，但信息準確 |
| **銀行融資 API 自動同步** | 銀行負責人手動報告 | 失去實時性，但信息準確 |
| **工地進度自動識別** | 工地人員手動報告進度 | 失去自動化，但系統仍可工作 |
| **NLP 自動理解** | 提供「選擇題」而非自由輸入 | 降低易用性，但大幅提高準確率 |
| **Web 儀表板實時更新** | 每天更新一次（批量） | 失去實時性，但信息同步 |
| **複雜權限管理** | 簡化為 3 種角色 | 靈活性降低，但易實現 |

**重點**：降級不影響核心價值，只是減少自動化程度

## 風險緩解策略

### 策略 1：分階段上線

```
不是「一次性建設 100% 功能」
而是「邊驗證邊升級」

PHASE 0（概念驗證）:
  • 證明技術可行
  • 用假想數據演示

PHASE 1（MVP）：
  • 一個真實項目
  • 有真實數據反饋
  • 識別真實問題

PHASE 2（擴展）：
  • 多項目同時進行
  • 積累經驗和數據
  • 優化系統

這樣的話，即使某個環節有問題，也是在可控範圍內
```

### 策略 2：準備降級方案

```
每個自動化功能都有「人工替代方案」
  • 自動同步 → 人工填表
  • 自動分類 → 人工分類
  • 自動預警 → 人工檢查

這樣系統不會「不可用」，只是「少一點自動」
```

### 策略 3：從簡到繁

```
不是一開始就做「全部 9 層圖譜」
而是：
  PHASE 0：基礎 3 層（進度 + 法規 + 角色）
  PHASE 1：加入 3 層（財務 + 風險 + 願景）
  PHASE 2：完整 9 層（加入決策 + 溝通 + 案例）

這樣複雜度可控，風險分散
```
