# agentic new_city Agent 主體規劃

## 系統定位

**agentic new_city** = 都市更新項目的「中樞神經系統」

### 角色定位
- 不是決策者（決策者是人）
- 不是執行者（執行者是各個單位）
- 而是**協調者、信息中樞、決策支持系統**

### 服務對象
- **政府**（看進度、知道誰在延誤）
- **建商**（看風險、找加速機會）
- **居民**（看決策、知道何時完成）
- **工程單位**（看依賴、知道何時開始）

---

## 核心目標

### 三層目標對齐
1. **政府目標**：建照核發、工程監督、防災檢查
2. **建商目標**：送審計劃書 → 取得建照 → 竣工交屋
3. **居民目標**：信息透明 → 利益公平 → 及時完成

### Agent 的使命
**統一的信息透明化 + 協調自動化**

## Agent 的推理引擎

### 三種 graphify 查詢模式

#### 模式 1：狀態查詢 (Status Query)
```
用戶：「現在進度多少？」
  ↓
Agent 執行：/graphify query "進度圖譜 當前狀態"
  ↓
返回結果包括：
  • 當前完成度百分比
  • 下一個里程碑及預計日期
  • 正在進行的並行工作
  • 已識別的瓶頸
  • 風險圖譜中的 active risks
```

#### 模式 2：路徑分析 (Path Analysis)
```
用戶：「怎樣加快進度？」
  ↓
Agent 執行：/graphify path "當前進度" "完成狀態"
  ↓
返回結果包括：
  • 最短路徑（所有依賴關係）
  • 可並行執行的任務
  • 瓶頸環節（關鍵路徑上的難點）
  • 時間成本（並行化的最大潛力）
```

#### 模式 3：衝突檢測 (Conflict Detection)
```
事件：新決策提交
  ↓
Agent 自動執行多個查詢：
  • /graphify query "新決策 vs 法規圖譜"
  • /graphify query "新決策 vs 風險圖譜"
  • /graphify query "新決策 vs 角色圖譜"
  ↓
自動生成警告和替代方案
```

### Agent 的 12 項核心能力

| # | 能力 | graphify 查詢 | 說明 |
|---|------|-------------|------|
| 1 | 進度查詢 | `/graphify query "進度圖譜"` | 隨時回答「進度多少」 |
| 2 | 下一步建議 | `/graphify path "當前→完成"` | 識別關鍵路徑和加速點 |
| 3 | 衝突預警 | `/graphify detect "衝突"` | 新決策違反法規/利益嗎 |
| 4 | 法規查詢 | `/graphify explain "條例"` | 「為什麼必須這樣做」 |
| 5 | 角色查詢 | `/graphify query "角色 X"` | 誰負責什麼、權限是什麼 |
| 6 | 融資狀態 | `/graphify query "財務圖譜"` | 錢夠嗎、進度如何 |
| 7 | 風險監控 | `/graphify query "風險圖譜"` | 有什麼可能出錯 |
| 8 | 決策支持 | `/graphify query "決策 X"` | 比較方案 A vs B |
| 9 | 類似案例 | `/graphify query "案例圖譜"` | 參考過去類似項目 |
| 10 | 溝通紀錄 | `/graphify explain "會議"` | 上次誰決定了什麼 |
| 11 | 自動預報 | 多層複合查詢 | 「如果現在不加速，會怎樣」 |
| 12 | 透明化報告 | 聚合多個查詢 | 自動生成周報、月報 |

## 信息流和數據流

### 完整的信息流動循環

#### 場景 1：日常進度更新循環
```
工地主任 → 提交「混凝土澆灌完成 80%」
       ↓
感知層：捕捉、去重、轉化為「進度圖譜節點更新」
       ↓
大腦層：
  /graphify query "混凝土澆灌狀態" → 更新進度
  /graphify path "當前→下一步" → 找出下一個關鍵路徑
  /graphify detect "有無風險" → 檢測風險
       ↓
執行層：
  • 更新進度表
  • 發送通知給所有人
  • 記錄於溝通圖譜
       ↓
所有利益相關者同時看到新進度

週期：實時（秒級）
```

#### 場景 2：決策衝突檢測循環
```
建商 → 提出「改用不同的鋼材供應商」
  ↓
感知層：捕捉、分類為「決策變更」
  ↓
大腦層：
  /graphify query "新供應商 vs 合約條款"
  /graphify query "新供應商 vs 原供應商"
  /graphify path "材料變更 → 竣工日期"
  /graphify query "材料變更 vs 質量標準"
  ↓
執行層：
  若無衝突 → 批准並記錄
  若有衝突 → 發送預警給相關方
  ↓
決策被改善或被延期

週期：小時級（新決策時觸發）
```

#### 場景 3：自動報告生成循環
```
每週五 17:00 系統自動執行
  ↓
大腦層：
  /graphify query "進度圖譜 本周變化"
  /graphify query "風險圖譜 狀態變化"
  /graphify query "決策圖譜 新決議"
  /graphify query "案例圖譜 類似經驗"
  ↓
執行層：
  • 聚合成結構化周報
  • 發送 Email（正式記錄）+ Telegram（快速通知）
  • 更新 Web 儀表板

週期：每週固定時間
```

## 關鍵風險和假設

### 風險 1：初始圖譜數據完整性
```
當前狀態：
  ✅ 進度圖譜：有初步規劃
  ✅ 法規圖譜：都更條例內容存在
  ⚠️ 角色圖譜：需要明確的專案參與者
  ⚠️ 案例圖譜：需要 3-5 個台北市案例

解決方案：
  • MVP 版本用「最少可行知識」（60% 覆蓋）
  • 邊運營邊補充（群眾外包）
  • 3 個月內達到 85% 覆蓋
```

### 風險 2：外部系統集成困難
```
當前狀態：
  ❌ 台北市都發局：無公開 API
  ❌ 銀行融資系統：無公開 API

降級方案：
  • 政府部分：人工填報表單
  • 銀行部分：負責人手動更新
  • 優先級：不影響 MVP 上線
```

### 風險 3：NLP 理解準確率
```
當前技術：
  ✅ Claude 在結構化數據理解上 95%+ 準確

降級方案：
  • 提供「選擇題」而不是自由輸入
  • 簡化 NLP，提高可靠性
  • 人工審核：每周檢查一次
```

### 風險 4：利益相關者接納度
```
降級方案：
  • 從「試點項目」開始，而不是全面推行
  • 選擇「願意合作」的開發商和政府人員
  • 提供多種輸入方式（Telegram / Email / 表單）
  • 强調「為他們服務」而不是「監控他們」
```

## 與引力理論的連接

### agentic new_city 如何實現引力理論

**數位資產引力理論的核心**：
> 資料流向哪裡，價值就累積在哪裡

**agentic new_city 的應用**：
- **傳統模式**：信息流向政府 & 建商 ≈ 利益流向他們
- **知識圖譜模式**：信息流向所有相關者 ≈ 利益均衡化
- **結果**：從「零和遊戲」變成「正和遊戲」

### Hub-and-Spoke 架構在 Agent 中的體現

```
Agent 作為中心 Hub：

  建商 \
  居民  > ──→ agentic new_city Agent ──→ 統一決策中樞
  政府  /
  工程單位

每一個參與者都是 Spoke，信息在 Hub 中流動和轉化
→ 實現透明化和協調自動化
```
